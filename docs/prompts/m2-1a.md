M2 の1本目として、実プロバイダ用の ExecutionAdapter を実装します。
作業前に最新の main から feat/m2-1a-provider-adapter ブランチを切ること。
設計書は §2.6 のステージ9、§5.8、§16-11（Execution Adapter 拡張ポイント）、
および ADR-0014（リトライ責務、ExecutionErrorType）を読む。

■ 前提（決定済み）
APAP は現時点で存在しないため、PEP の内部に暫定の実行アダプタを置く。
これは設計上の後退であり、APAP 実装時に置き換える前提であることを
ADR に明記すること。domain / core / application は一切変更しないこと
（変更が必要になったら、それは境界が漏れているサインなので報告すること）。

■ 実装前に決めること（方針を提示して承認を得てから着手）

1. アダプタの配置
   FakeExecutionAdapter は plugins/execution-fake にあります。
   実プロバイダ用アダプタも plugins/execution-<name> として
   サブプロジェクトにするのが §16-11 の拡張ポイントと一貫すると考えますが、
   判断と根拠を示してください。
   プラグインにする場合、ADR-0003 のパッケージ命名規則
   （promptengine.plugin.<category>.<name>）に従い、
   bootstrap への testImplementation 配線と ArchUnit 規約6 の対象に
   含めることを忘れないこと。

2. どのプロバイダを最初に繋ぐか
   1本だけ選んでください。複数を同時に実装しないこと。
   選定理由と、プロバイダ固有の知識がそのサブプロジェクト内に
   完全に閉じることを示してください。

3. CONNECT_TIMEOUT と READ_TIMEOUT を実際に区別できるか（重要）
   ADR-0014 で「接続確立前のタイムアウトはリトライ可、
   応答待ちのタイムアウトはリトライ不可」と決めましたが、
   これは Fake でしか検証されていません。
   実際の HTTP クライアントで、この2つを例外の型やフラグから
   確実に区別できるかを確認してください。
   区別できない場合、ADR-0014 の前提が崩れるので、
   その事実と代替案（安全側に倒す等）を報告すること。

4. usage が返らない場合の扱い
   プロバイダによっては inputTokens / outputTokens が
   返らない、あるいは一部しか返らないことがあります。
   コスト算出が不能になるため、その場合の扱いを決めてください
   （推定値を使う / 記録しない / エラーにする のいずれか。
    「推定値を使う」場合は、推定であることがデータ上で区別できること）。

5. 認証情報の扱い
   プロバイダの API キーは SecretManagerAdapter 経由でのみ取得し、
   SensitiveValue でラップすること。
   本来 APAP の責務である以上、PEP のコード・ログ・例外・メトリクス・
   設定ダンプのいずれにも実値が現れないことを、
   M1 と同じ厳密さで経路別テストにより担保すること。

■ 実装スコープ
- plugins/execution-<name>（または決定した配置）に実プロバイダ用の
  ExecutionAdapter 実装
- プロバイダのエラー → ExecutionErrorType（CONNECT_TIMEOUT / READ_TIMEOUT /
  RATE_LIMITED / SERVER_ERROR / CLIENT_ERROR / UNKNOWN）への写像
- 429 応答時の Retry-After ヘッダの尊重（存在する場合）
- RenderedPrompt の抽象 role（system / user / assistant / tool）から
  プロバイダ形式への変換。この変換をアダプタ内に閉じること
- usage / latency の取得と RawResponse への詰め替え
- ストリーミングは対象外（P7 で将来別インターフェースとする決定済み）

■ テスト要件
- スタブサーバ（WireMock 等）による契約テスト
  - 正常応答、429（Retry-After あり / なし）、5xx、4xx、
    接続タイムアウト、応答タイムアウト、不正 JSON の各ケース
  - それぞれが期待する ExecutionErrorType に写像されること
- 認証情報が、ログ・例外メッセージ・メトリクスのラベル・
  設定ダンプのいずれにも出ないこと（経路ごとに独立したテスト）
- role 変換が仕様どおりであること
- usage 欠落時の挙動（上記4の決定に従う）
- 実プロバイダへの実接続は M2-1c で行うため、このPRでは行わないこと
- 新規追加コードの未カバー分岐を3分類で監査
- カバレッジは buildSrc の下限を下回らないこと

完了時に ./gradlew build ktlintCheck detekt test の結果、テスト件数、
カバレッジ（行・分岐）、分岐監査の結果、
および方針1〜5 の決定内容を報告してください。
