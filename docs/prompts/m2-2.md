# M2-2 プロンプト（ReviewCase）

M2 として ReviewCase Aggregate と承認系 API を実装します（Issue #9 の回収）。
作業前に最新の main から feat/m2-2-review-case ブランチを切ること
（ブランチへ switch してから作業を始めること）。
設計書は §4.3（ReviewCase の不変条件）、§2.5（ライフサイクル遷移とガード）、
§14（PromptReviewRequested / PromptApproved / PromptRejected、発火元は ReviewCase）、
§12（review_cases / approvals テーブル）、§13.1（承認系エンドポイント）を読む。

## ■ 実装前に決めること（方針を提示して承認を得てから着手）

1. Prompt と ReviewCase の整合性（最重要）
   approve が成立すると ReviewCase の状態が変わり、
   同時に Prompt の Version が Approved へ遷移します。
   これは2つの Aggregate にまたがる更新です。
   DDD の原則では1トランザクション1アグリゲートですが、
   ここで結果整合にすると「承認されたのに Approved になっていない」瞬間が生じます。
   - 同一トランザクションで両方更新するか
   - イベント駆動で結果整合にし、その間の状態をどう見せるか
   判断と根拠を示してください。妥協する場合は何を妥協したかを明記すること。

2. ApprovalPolicy の適用単位
   §2.5 は「必要承認数（既定1、設定可）」としています。
   - Prompt 単位 / カテゴリ単位 / グローバル のどこで設定するか
   - 設定が無い場合の既定値
   - 変更した場合、進行中の ReviewCase に影響するか

3. 自己承認の扱い
   4-eyes 原則（作成者と承認者が別人）を強制するか。
   強制する場合、単独利用時にレビューが完了できなくなるため、
   設定で無効化できる必要があります。既定値をどちらにするかを判断すること。

4. 却下後のフロー
   reject で Draft に戻った後、再度 submitForReview したときに
   ReviewCase は新規作成されるか、同じものが再開されるか。
   過去のレビューコメントが引き継がれるかどうかも決めること。

## ■ 実装スコープ
- ReviewCase Aggregate（domain）
  ReviewComment / ApprovalRecord、§4.3 の不変条件
  （承認数 ≥ ApprovalPolicy.required で承認確定）
- ApprovalPolicy（上記2の方針に従う）
- Domain Event: PromptReviewRequested / PromptApproved / PromptRejected
  発火元は ReviewCase（§14 の表のとおり）。封筒8フィールドを厳守
- ReviewCaseRepository と永続化（§12 の review_cases / approvals）
  P2 で確立した Memento + @PersistenceApi パターンを踏襲すること
- Application ハンドラ: submitForReview / approve / reject
  Prompt 側のガード（submitForReview は Validation 合格、
  approve は承認数充足）を実データから評価すること
- REST エンドポイント3件（§13.1）
  スコープは prompt:review / prompt:approve
- E2E スモークテストを HTTP のみで通るよう修正する
  （現在 Approved 化を Repository 直叩きで迂回している箇所を解消）

## ■ テスト要件
- §4.3 の不変条件（承認数 ≥ required で確定）を破ろうとするテスト
- 承認数不足で approve を試みた場合に Prompt が Approved にならないこと
- 自己承認の可否（上記3の決定に従う）
- reject → 再 submitForReview のフロー（上記4の決定に従う）
- 3イベントが §14 の封筒形式で発行され、Audit に記録されること
  （M1 の間これらが監査に残らなかった穴が塞がることの確認）
- 認可: review / approve スコープの有無による 200 / 403
- E2E: Prompt 作成 → Version 作成 → submit-review → approve → publish → render が
  すべて HTTP 経由で成功すること
- 新規追加コードの未カバー分岐を3分類で監査
- カバレッジは buildSrc の下限を下回らないこと

完了時に ./gradlew build ktlintCheck detekt test の結果、テスト件数、
カバレッジ（行・分岐）、分岐監査の結果、統合テストの CI 実行件数
（JUnit XML の実数）、および E2E が Repository 直叩きなしで
通ることの確認結果を報告してください。

## 優先順位の背景

M2の作業順は次の理由による（穴を先に、機能追加を後に）。

| 順 | 項目 | 理由 |
|---|---|---|
| 1 | #9 ReviewCase / 承認系 API | 穴を塞ぐ作業。承認遷移が監査に残らず、API からも到達できない。E2E も Repository 直叩きで迂回している |
| 2 | #15 → #77 イベント → キャッシュ | Template/Fragment の変更が監査に残らない穴を塞ぎ、NFR-001 / NFR-002 の検証を解禁 |
| 3 | FR-015 Experiment Engine | 唯一の完全未実装。A/B・Canary・Benchmark。単体では大きいが Fake で完結する |

1 が設計上の山。「承認されたのに Approved になっていない瞬間」を許容するかどうかは、
ガバナンス基盤としての性格を決める。同一トランザクションにすれば単純だがAggregate境界を
跨ぐ。結果整合にすれば原則は守れるが、その中間状態をAPIがどう見せるかを決める必要がある。
どちらでも構わないが、選ばなかった方の何を諦めたかを明記すること。
