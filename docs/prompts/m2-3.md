# M2-3 プロンプト（イベント → キャッシュ）

M2 として Template/Fragment の Domain Event（Issue #15）と、
CompiledPrompt のキャッシュ（Issue #77）を実装します。
作業前に最新の main から feat/m2-3-events-cache ブランチを切ること。
設計書は §14（イベント一覧）、§16-9（Cache 拡張ポイント）、§2.6 のステージ1〜3、
§5.1〜5.2 のシーケンス、§2.8（Secret 変数の扱い）、ADR-0008 を読む。

## ■ 実装前に決めること（方針を提示して承認を得てから着手）

1. Template/Fragment イベントの定義とトピック
   設計書§14 には Template/Fragment のイベントが1行もありません（ADR-0008 で
   意図的に見送った経緯）。今回追加するので、§14 の表に行を足す必要があります。
   - イベント名（Prompt 側の命名と一貫させること）
   - 発火元と購読先
   - どのトピックへ流すか（既存の pe.prompt に載せるか、新設するか）
   設計書§14 と ADR の両方を更新すること。

2. キャッシュキーの設計
   CompiledPrompt は参照解決済みの成果物です。
   - キーに何を含めるか（promptKey / versionRef / CompositionMode /
     解決された依存のバージョン集合 など）
   - versionRef が latest や alias の場合、publish で指す先が変わる。
     この扱いをどうするか

3. 無効化の正しさ（最重要）
   Fragment を publish したとき、それを include している全 Prompt の
   キャッシュを無効化する必要があります。
   - 逆依存の探索に DependencyRepository.findInbound を使う想定でよいか
   - SemVer 範囲指定（@^2 等）の場合、新しく publish されたバージョンが
     その範囲にマッチするかの判定が必要になる。どう扱うか
   - 逆依存が深い場合（Fragment → Template → Prompt）の連鎖をどこまで辿るか
   - 無効化に漏れがあると「古い Fragment の内容で実行され続ける」という
     静かな不具合になります。漏れが無いことをどう保証するかを示してください

4. Secret とキャッシュの境界
   設計書§2.8 は「Secret を含む Render 結果のキャッシュ禁止」と定めています。
   CompiledPrompt は変数束縛より前の成果物なので Secret を含みませんが、
   その前提が実装上も保証されていることを示してください
   （将来 Render 結果もキャッシュしたくなったときに、
    この境界が曖昧だと事故になります）

5. 複数インスタンスでの無効化
   イベント購読で各インスタンスが無効化する形になると思いますが、
   イベント到達前に古い値が読まれる窓が生じます。
   この窓をどう扱うか（許容する / TTL で上限を設ける / 他）。

## ■ 実装スコープ
- Template / Fragment の Domain Event 発行（Issue #15 の回収）
  封筒8フィールド厳守。Audit に記録されることの確認を含む
  （M1 の間これらが監査に残らなかった穴が塞がる）
- PromptCache の実装（設計書§3.4 の Interface、§16-9 の拡張ポイント）
- Load / Merge / Import ステージでのキャッシュ利用（§2.6、§5.1〜5.2）
- Publish 系イベントによる無効化（Prompt / Template / Fragment）
- NFR-002（キャッシュヒット時 p99 ≤ 20ms）の測定
  M1 の P11 で作った測定手順を流用し、同じ条件（コンテナ、リソース制限、
  ウォームアップ回数）で測ること
- 設計書§1.9 の NFR-002 行から「M1 では未検証」の注記を更新

## ■ テスト要件
- Template / Fragment の各イベントが発行され、Audit に記録されること
- キャッシュヒット / ミスの動作
- 無効化: Prompt / Template / Fragment それぞれの publish で、
  影響を受けるキャッシュが確実に落ちること
  特に「Fragment を publish したら、それを include している Prompt の
  CompiledPrompt が古いままにならない」ことを、
  実際に内容を変えて検証すること（キーの一致だけでなく中身で確認）
- SemVer 範囲指定の場合の無効化（範囲にマッチする新バージョンが出たとき）
- 複数インスタンス想定（イベント購読による無効化）の統合テスト
- キャッシュを有効にしても renderHash が変わらないこと（決定性の維持）
- 新規追加コードの未カバー分岐を3分類で監査
- カバレッジは buildSrc の下限を下回らないこと

完了時に ./gradlew build ktlintCheck detekt test の結果、テスト件数、
カバレッジ（行・分岐）、分岐監査の結果、統合テストの CI 実行件数、
および NFR-002 の実測値（測定条件付き）を報告してください。

## 山

3が今回の山です。キャッシュの無効化漏れは、テストが通るのに古い内容で動き続けると
いう最悪の形で現れます。「キーが一致すること」ではなく「内容が更新されていること」で
検証してください。
