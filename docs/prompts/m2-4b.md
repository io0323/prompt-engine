FR-015 の残りとして Benchmark（オフライン評価）を実装します。
作業前に最新の main から feat/m2-4b-benchmark ブランチを切ること。
設計書は §1.8 FR-015、§2.12（Evaluation仕様、特に Accuracy / Consistency /
Determinism の「Benchmark時」の記述）、§4.3（Experiment の不変条件）、
§12（experiments テーブルの type 列）、§16-6（Evaluation Rule 拡張ポイント）を読む。

■ 実装前に決めること（方針を提示して承認を得てから着手）

1. Benchmark と Experiment Aggregate の関係（最重要）
   §12 は experiments.type に BENCHMARK を含めており、同じテーブルを
   使う想定に見えます。しかし §4.3 の Experiment の不変条件は
   「Variant 2..n」「配分合計 = 100%」であり、これはオンラインの
   トラフィック分割を前提としたものです。Benchmark はオフライン評価なので
   Variant もトラフィック配分も持ちません。
   - 同じ Aggregate に載せて不変条件を type 別に分岐させるか
   - 別 Aggregate にするか
   M2-4a で「Published 同時1件」を緩めずに別経路で解決したのと同様、
   既存の不変条件を弱めない形を優先してください。
   判断と、選ばなかった側の何を諦めたかを示すこと。

2. Golden Dataset のモデル
   §2.12 は Accuracy を「Golden Dataset 正解率」と定めていますが、
   設計書§12 に該当するテーブルがありません。
   - データセットの構造（入力変数の組、期待出力、メタデータ）
   - どこに保持するか（新規テーブル / Object Storage / 外部参照）
   - Prompt / Version との関連（データセットは Prompt 単位か、共有か）
   スキーマ追加になるので ADR と設計書§12 の両方を更新すること。

3. Benchmark 実行の起動方式
   データセット件数 × 試行回数だけ実行するため、同期 API では収まりません。
   - 非同期ジョブとして起動し、進捗を照会する形にするか
   - 実行中の中断、失敗時の再開をどう扱うか
   - 既存の Event Bus / Outbox を使うか、別の仕組みにするか
   §13.1 に Benchmark 用のエンドポイントが定義されていないため、
   追加するなら ADR を起こしてから §13.1 に行を足すこと。

4. Accuracy の判定方法
   期待出力との「一致」をどう定義するか。
   - 完全一致 / 正規化後の一致 / 構造的一致（JSON のキー単位）/ 意味的類似
   - §16-6 の EvaluationRule 拡張ポイントとして差し替え可能にすること
   - M2 の既定実装として何を提供するか

5. Consistency / Determinism の実行コスト
   §2.12 は Consistency を「同一入力 N 回実行の出力類似度」、
   Determinism を「temperature=0 でのバイト一致率」と定めています。
   どちらも N 回の実行が必要です。
   - M2 では FakeExecutionAdapter 前提でよいか
     （実プロバイダだとデータセット件数 × N 倍の課金が発生する）
   - N の既定値と、設定で変更できること
   - 実プロバイダで実行する場合の事前コスト見積もりを
     利用者に示す手段を設けるか

6. 評価対象の指定
   単一 Version を評価するのか、複数 Version を比較するのか。
   複数比較する場合、A/B の Variant とは別の概念になるため、
   どう表現するかを決めること。

■ 実装スコープ
- Benchmark の実行と結果記録（上記1の判断に従う）
- Golden Dataset の永続化と管理
- Accuracy / Consistency / Determinism の EvaluationRule 実装
  （§16-6 の拡張ポイント経由）
- Benchmark 用エンドポイント（ADR を起こしたうえで §13.1 に追加）
  追加するエンドポイントには必ず @PreAuthorize を付けること
  （#115 で追加した ArchUnit ルールが強制します）
- Benchmark 結果の EvaluationRecord への記録

■ テスト要件
- Accuracy / Consistency / Determinism がそれぞれ正しく算出されること
  （既知のデータセットに対して期待どおりのスコアが出ること）
- Benchmark 実行中の中断・再開（上記3の決定に従う）
- 新規エンドポイントの認可テスト（200 / 403 / 401）
- §4.3 の不変条件が Benchmark によって壊れないこと
  （上記1の判断に応じたテスト）
- 新規追加コードの未カバー分岐を3分類で監査
- カバレッジは buildSrc の下限を下回らないこと
