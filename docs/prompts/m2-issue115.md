Issue #115 を回収します。@PreAuthorize が付いた21エンドポイント（8 Controller）に
対する認可テストを追加します。
作業前に最新の main から fix/issue-115-authorization-tests ブランチを切ること。
設計書は §13.1（エンドポイントとスコープの対応表）、§13.3（401 / 403 のコード）を読む。

■ 前提
- 参照実装は #114 で追加した ExperimentControllerAuthorizationTest。
  同じ軽量パターン（MockMvc + モック JWT、DB・コンテナ不要）を踏襲すること
- Issue #115 に記録した jwt().authorities(...) の注意点を確認してから着手すること

■ 実装スコープ

1. 振る舞いのテスト（21エンドポイント）
   各エンドポイントについて3ケース:
   - 必要なスコープを持つトークン → 2xx（または認可以外の理由による
     4xx。認可で弾かれていないことが確認できればよい）
   - 不足したスコープを持つトークン → 403 / PERMISSION_DENIED
   - トークン無し → 401 / UNAUTHENTICATED
   スコープの対応は設計書§13.1 の表を正とすること。
   実装と §13.1 が食い違っている箇所があれば、修正せずにまず報告すること。

2. 構造的なガード（こちらがより重要）
   21件のテストを手で書いても、22件目のエンドポイントが
   @PreAuthorize 無しで追加されれば同じ穴が空きます。
   以下を検証するテストを追加してください。
   - Controller の全ての公開ハンドラメソッド（@GetMapping / @PostMapping /
     @PatchMapping / @DeleteMapping 等が付いたもの）に
     @PreAuthorize が付いていること
   - 意図的に認可不要なエンドポイントがあれば、明示的な許可リストで
     除外し、その理由をコードに書くこと
   - 新しいエンドポイントを @PreAuthorize 無しで追加すると、
     このテストが落ちることを実測で確認すること
     （一時的にアノテーションを外して落ちることを確認し、戻す）

3. スコープ対応の可視化
   「どのエンドポイントがどのスコープを要求するか」を、
   設計書§13.1 の表と突き合わせられる形にしてください。
   テストのパラメータ化などで一覧化できると、
   §13.1 との乖離が発見しやすくなります。

■ 検証
- 追加したテストが実際に機能することを確認する
  代表的な Controller 1つについて、@PreAuthorize を一時的に外し、
  対応する 403 のテストが落ちることを実測してから戻すこと
  （このプロジェクトで新しいガードを入れるたびに行っている手順）
- 全21エンドポイント × 3ケースの実行件数を、
  CI の JUnit XML の実数で確認して報告すること

■ 報告事項
- 設計書§13.1 の表と実装のスコープ対応に食い違いがあれば列挙すること
- テストを書く過程で見つかった不具合があれば報告すること
  （#114 では認可テストを書いたことで AuthorizationDeniedException の
   500 問題が見つかっています。同種の発見がありうる領域です）

完了時に ./gradlew build ktlintCheck detekt test の結果、テスト件数、
カバレッジ（行・分岐）、CI での実行件数を報告してください。

---

補足（ユーザー、プロンプト提示時のコメント）:

2 の構造的ガードが本命です。21件のテストは今ある穴を塞ぎますが、次に追加されるエンドポイントは守りません。「全ハンドラに `@PreAuthorize` が付いていること」を機械的に検証しておけば、認可を忘れたエンドポイントはビルドが通らなくなります。ArchUnit の規約6や `ProviderNameContainmentTest` と同じ考え方です。

これが片付いたら M2-4b（Benchmark）に進みます。
