# P10b: Evaluation Engine / Audit Engine / 実DLQ / execution_logs

P10 の 2本目として、Evaluation Engine と Audit Engine、実 DLQ、
execution_logs の書き込みを実装します。
作業前に最新の main から feat/p10b-evaluation-audit ブランチを切ること。
設計書は §2.12（Evaluation仕様)、§2.15（Monitoring)、§14（イベント一覧)、
§12（ER図の execution_logs / audit_logs）を読む。

## 実装前に決めること（方針を提示して承認を得てから着手）

1. execution_logs を誰が書くか
   Pipeline の Audit ステージが書くのか、PromptExecuted を購読する
   Subscriber が書くのかを判断してください。
   Pipeline のステージは「既存 Engine への薄い委譲」に留める方針なので、
   購読側が自然だと考えていますが、判断と根拠を示すこと。
   10a で決めた冪等性（UNIQUE(event_id) + ON CONFLICT DO NOTHING）を
   ここにも適用すること。

2. Audit ステージ失敗時の実 DLQ の形態（Issue #37）
   - 専用テーブルか、Broker の DLQ トピックか
   - 退避したレコードの再処理手段（手動か自動か）
   - 退避が発生したことをどう検知するか（メトリクス／アラート）

3. archive ガードの execution_logs ベース化（Issue #48）
   現在 archive は force=true のみ受け付ける状態です。
   execution_logs が書かれるようになったら、
   「直近 N 日間に実行が無いこと」をガードにできます。
   - N の既定値と、設定で変更可能にする方法
   - execution_logs にデータが無い（＝一度も実行されていない）場合の扱い
     （「参照ゼロ」と「記録が無いだけ」を区別できるか）
   - 区別できないなら、その限界を明示したうえでどう扱うかを決めること

   補足: 3の「参照ゼロ」と「記録が無いだけ」の区別は、実は難しい論点です。
   execution_logs が P10b 以降にしか存在しない以上、それ以前から存在する
   Prompt は「実行記録が無い」状態になります。ガードを素直に実装すると、
   古い Prompt が全部 archive 可能になってしまう。ここをどう扱うかは
   方針提示の段階で見せること。

## 実装スコープ

- EvaluationRule インターフェース（domain）と EvaluationEngine 実装（core）
  - PromptExecuted を購読して非同期評価
  - M1 の評価器: Latency / TokenUsage / Cost（usage × ModelProfile 単価）
  - Quality 系は Plugin で後から足せる構造にすること
  - 結果を EvaluationRepository に保存し PromptEvaluationCompleted を発行
- AuditEngine
  - 全イベントを購読して audit_logs へ追記
  - payload の Secret がマスク済みであることをテストで保証すること
- execution_logs の書き込み（上記1の方針に従う）
- 実 DLQ（Issue #37 の回収）
- archive ガードの execution_logs ベース化（Issue #48 の回収）
- Cache Invalidator（PromptPublished 等で invalidateByPrompt）
- Search Indexer は M1 では簡易実装でよい

## テスト要件

- execution_logs / audit_logs の書き込みが、同一イベントの再配信で
  二重にならないこと（10a の冪等性方針が効いていること）
- Audit の payload に Secret の実値が出ないこと（経路別テスト）
- DLQ: Audit の書き込みが失敗した場合に退避され、
  本流が失敗しないこと。退避が検知可能であること
- archive ガード: 直近実行がある場合に archive が拒否され、
  無い場合に許可されること。force=true で常に通ること
- Evaluation が同期的に本流をブロックしないこと
- 新規追加コードの未カバー分岐を3分類で監査
- カバレッジは buildSrc の下限を下回らないこと
