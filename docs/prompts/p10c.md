# P10c: Monitoring / IN_PROGRESS 滞留対策

M1 の最後から2番目です。

P10 の 3本目として、Monitoring と IN_PROGRESS 滞留対策を実装します。
作業前に最新の main から feat/p10c-monitoring ブランチを切ること。
設計書は §2.15（Monitoring仕様）、§1.9（非機能要件）を読む。

## 実装前に決めること（方針を提示して承認を得てから着手。実装は承認後）

1. メトリクスのラベル設計（カーディナリティ）
   §2.15 のメトリクス（pipeline_stage_duration / render_count /
   cache_hit_ratio / validation_failure_count / token_usage_total /
   cost_total / execution_success_rate）に promptKey や version を
   ラベルとして付けると、Prompt 数 × バージョン数だけ時系列が増え、
   監視基盤側で破綻します。
   - どのメトリクスにどのラベルを付けるかを表で示すこと
   - 高カーディナリティになりうるラベル（promptKey / version / traceId）を
     どう扱うか（付けない / 上位N件のみ / 別の集計経路に回す）
   - コストとトークンは Prompt 単位で見たい要求があるはずなので、
     それをメトリクスで解決するのか、execution_logs のクエリで解決するのかを
     切り分けること

2. OTel エクスポータの構成
   - 送信先の設定方法（環境変数 / 設定ファイル）
   - Collector が存在しない環境（ローカル・CI）で、
     起動が失敗したりテストが遅くなったりしないこと
   - 未設定時の既定挙動（no-op エクスポータ等）

3. LogSanitizer をどう強制するか
   秘密がログに出ない保証を、開発者が呼び出しを忘れうる形にしないこと。
   これまで P4 / P6 / P7 で「経路別テスト」を積んできましたが、
   ログは新しい出力箇所が増え続ける性質があるため、
   呼び出し規約ではなく構造で担保する方法を提案してください
   （ログ出力の共通経路にサニタイズを挟む、appender / encoder 層で処理する 等）。
   P7 で RenderHashCalculator を「呼び忘れようがない単一入口」にしたのと
   同じ考え方を適用すること。

4. IN_PROGRESS 滞留対策（Issue #50）
   IdempotentCommandExecutor の IN_PROGRESS 予約が、
   プロセスクラッシュ時に解放されず永久にブロックされる件です。
   10a の Outbox で採用した3段階 Claim + claim_timeout + フェンシングと
   同じ構造で解けるはずなので、パターンを揃えられるか検討してください
   （揃えられないなら理由を示すこと）。

## テスト要件

- メトリクスが実際に記録されること（値と、付与されたラベル）
- 高カーディナリティのラベルが付いていないことを検証するテストを置くこと
  （後から誰かが promptKey を足したときに落ちるように）
- traceId がリクエスト全体を貫通し、イベントとログにも載ること
- LogSanitizer: 秘密が出ないこと、および秘密でない値が壊れないこと
  （P10b の inputTokens 過剰マスクと同じ失敗を防ぐため、両方向を検証すること）
- IN_PROGRESS: クラッシュを模した状況で予約が滞留せず、
  タイムアウト後に別リクエストが処理できること
- 新規追加コードの未カバー分岐を3分類で監査
- カバレッジは buildSrc の下限を下回らないこと（infrastructure の集約ゲートを含む）

## 補足（カーディナリティ方針の事前示唆）

1 のカーディナリティは、監視を入れる段で必ず問題になるところです。
promptKey をラベルに付けたくなりますが、Prompt が数千・バージョンが
数十になると時系列が爆発し、監視基盤のコストと応答性が壊れます。
Prompt 単位のコスト分析は execution_logs のクエリで行い、
メトリクスは低カーディナリティに保つのが定石です。方針提示でそこを見せてください。
