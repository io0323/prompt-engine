## 実装前に決めること（方針を提示して承認を得てから着手）

1. Outbox → Broker 中継の実装形態
   - ポーリングワーカー方式か、他の方式か
   - ポーリング間隔、バッチサイズ、失敗時のリトライとバックオフ
   - 複数インスタンスが同時に動いた場合に同じ行を二重配信しない仕組み
     （行ロック、advisory lock、パーティション等）

2. at-least-once 配信下での購読側の冪等性
   Outbox + Broker は原理的に at-least-once になります。
   同じイベントが2回届いたときに、Audit が二重記録したり
   キャッシュ無効化が過剰に走ったりしないための方針を示してください。
   （eventId による重複排除を購読側に持たせるのが素直だと考えていますが、
    判断と、どこに重複排除の状態を持つかを提示してください）

3. ローカルと CI での Broker の扱い
   - 統合テストで Broker をどう起動するか（Testcontainers）
   - CI の実行時間への影響見積もり
   - Broker が起動できない環境でのテストの扱い
     （スキップさせないこと。0件ガードと同じ問題になります）

     ガード自体をテストで検証し続けられる形にすること）

## テスト要件

- Outbox に書かれたイベントが Broker へ中継されること（Testcontainers 使用）
- 中継の途中でプロセスが落ちた場合に、イベントが失われないこと
- 同じイベントが2回配信されたときに購読側が二重処理しないこと
- 複数インスタンス想定での二重配信が起きないこと
- Broker 起動を伴う統合テストが CI で実際に実行されたことを、
  JUnit XML の実数で確認すること（0件ガードが効いていることも確認）
- 新規追加コードの未カバー分岐を3分類で監査（CLAUDE.md の標準手順）
- カバレッジは buildSrc の下限を下回らないこと

## 背景（P10分割の経緯）

§6.12 の内容に加えて Issue が5件（#35 / #37 / #38 / #11 / #48 / #50）ぶら下がっており、1 PR には収まらないため P10 を3本に分割した。
