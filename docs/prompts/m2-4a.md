FR-015 プロンプト（Experiment Engine）

分量が大きいので 2本に分けることを前提にしています。docs/prompts/m2-4a.md に保存してから着手してください。

FR-015（Experiment Engine）を実装します。分量が大きいため2本に分け、
本 PR は A/B テストと Canary（オンライン実験）を対象とします。
Benchmark（オフライン評価）は次の PR で扱います。
作業前に最新の main から feat/m2-4a-experiment ブランチを切ること。
設計書は §1.8 FR-015、§4.3（Experiment の不変条件）、§4.4（TrafficPolicy）、
§4.5（PromotionService）、§2.5（Published は同時に1Version）、§12（experiments /
variants テーブル）、§13.1（experiments 系エンドポイント）、§14（Experiment 系イベント）、
§16-12（Experiment Strategy 拡張ポイント）を読む。

■ 実装前に決めること（方針を提示して承認を得てから着手）

1. 「Published は同時に1Version」との整合（最重要）
   §4.3 は Prompt の不変条件として「Published は同時に1Version」を定め、
   Prompt Aggregate がこれを強制しています。
   一方 §2.5 は「Experiment 中は Variant として複数配信可」としています。
   この2つをどう両立させるかを決めてください。
   - Variant が参照する PromptVersion はどの状態か
     （Approved のまま配信する / 複数 Published を許す / 別の扱い）
   - Prompt Aggregate の不変条件を緩めるのか、
     Experiment 側が通常の解決経路を迂回するのか
   - 緩める場合、何が守られなくなるかを明記すること
   P1 から守ってきた不変条件に触れる可能性があるので、
   ここは特に慎重に判断してください。

2. Variant 割当がどこで行われるか
   Pipeline のどの時点で「どの Version を使うか」が決まるか。
   - Load ステージ（§2.6 ステージ1）で Experiment を考慮するのか
   - その前段で versionRef を解決してから Pipeline に渡すのか
   Pipeline に手を入れる場合、P8 で確立した「ステージは既存 Engine への
   薄い委譲に留める」方針を崩さないこと。

3. Sticky 割当
   §4.4 の TrafficPolicy は sticky key（userId 等）を持ちます。
   - sticky key をどこから取るか（PromptRequest / Context の user スコープ）
   - sticky key が無い呼び出しの扱い
   - 同一 sticky key に対して常に同じ Variant が割り当たることを
     どう保証するか（ハッシュベースか、割当の永続化か）

4. 実験実行の再現性と監査
   Experiment は同じ入力に対して異なる Version を返します。
   これは P6 で保証した renderHash の決定性を壊すものではありませんが、
   「過去の実行を再現できること」（§2.14 の監査要件）を満たすには、
   どの Variant が使われたかが記録されている必要があります。
   - execution_logs / audit_logs / PromptExecuted イベントの
     どこに variant を記録するか
   - スキーマ変更が必要なら ADR と設計書§12 の両方を更新すること

5. 統計判定の範囲
   §4.5 の PromotionService は「統計的有意判定後」に勝者を昇格するとしています。
   - どの指標で判定するか（§2.12 の7指標のうち、M2 で使えるのは
     Latency / TokenUsage / Cost の3つ）
   - どの検定を用いるか、必要な最小サンプル数
   - 判定を自動にするか、結果を提示して人が決める形にするか
   厳密な統計処理を作り込むとフェーズが肥大するので、
   M2 でどこまでやるかの線引きを明示してください。

6. Canary と A/B の違い
   - Canary は重みを段階的に変えていく運用が一般的ですが、
     自動で変えるのか、API 経由で人が変えるのか
   - Canary 固有の中止条件（エラー率が閾値を超えたら自動停止 等）を
     設けるかどうか

■ 実装スコープ
- Experiment Aggregate（domain）
  Variant(2..n)、TrafficPolicy、ExperimentStatus
  §4.3 の不変条件（配分合計 = 100%、Running 中の Variant 削除禁止）
- TrafficSplitStrategy（§16-12 の拡張ポイント）
  既定実装は重み付きランダム + sticky
- ExperimentRepository と永続化（§12 の experiments / variants）
  P2 の Memento + @PersistenceApi パターンを踏襲
- Domain Event: ExperimentStarted / ExperimentStopped /
  ExperimentWinnerDeclared / ExperimentCompleted
  トピックは pe.experiment（§14）。封筒8フィールド厳守
- PromotionService（§4.5）
- Application ハンドラと REST エンドポイント（§13.1）
  POST /experiments、start / stop、GET /experiments/{id}/results、promote
- Variant 別の EvaluationRecord 集計（§12 の evaluation_records.variant_id）

■ スコープ外
- Benchmark（次の PR）
- 多腕バンディット等の高度な戦略（§16-12 の差替例。拡張ポイントは用意するが
  既定実装のみ）

■ テスト要件
- §4.3 の不変条件を破ろうとするテスト（配分合計 ≠ 100%、
  Running 中の Variant 削除）
- トラフィック分割が指定した重みに従うこと（統計的な範囲で）
- 同一 sticky key が常に同じ Variant に割り当たること
- Experiment 実行後、どの Variant が使われたかが記録され、
  過去の実行を再現できること
- Experiment 停止後は通常の Version 解決に戻ること
- 4イベントが §14 の封筒形式で発行され、Audit に記録されること
- 認可: 各エンドポイントのスコープ有無による 200 / 403
- 新規追加コードの未カバー分岐を3分類で監査
- カバレッジは buildSrc の下限を下回らないこと

完了時に ./gradlew build ktlintCheck detekt test の結果、テスト件数、
カバレッジ（行・分岐）、分岐監査の結果、統合テストの CI 実行件数
（JUnit XML の実数）を報告してください。

補足（ユーザーからの追加コメント）:

1 が今回の山です。「Published は同時に1Version」は P1 で最初に実装した不変条件で、以降のすべてがその上に乗っています。Experiment のために緩めるなら、何が守られなくなるかを正確に把握したうえで決めてください。私の見立てでは、不変条件は維持したまま Experiment 側が別経路で Variant を解決する形（Published は1つのまま、Variant は Approved 状態の Version を参照する）が素直だと思いますが、判断は方針提示で見せてください。
