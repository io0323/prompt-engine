M2-1 の最終として、本番 DI 配線と実プロバイダでの疎通確認を行います。
作業前に最新の main から feat/m2-1c-real-execution ブランチを切ること
（ブランチへ switch してから作業を始めること）。
設計書は §2.11（ModelProfile）、§2.12（Cost 算出）、ADR-0014、ADR-0029 を読む。

■ 実装前に決めること（方針を提示して承認を得てから着手）

1. ModelProfile の供給源
   APAP が存在しないため、maxContextTokens / costPerToken / capabilities を
   取得できる外部ソースがありません。
   - これらを設定として管理する方法（どのファイル、どの粒度）
   - 価格改定やモデル追加への追随手順（誰がいつ更新するか）
   - 設定値が実態と乖離した場合に何が壊れるか
     （コスト集計の誤り、トークン予算判定の誤り）と、その検知手段
   「APAP 実装時にメタデータ取得へ移行する」ことを ADR に明記すること

2. リトライ責務（Issue #31 の本題）
   APAP が存在しない現状では、リトライは PEP が全面的に持ちます。
   - この事実を ADR に記録し、Issue #31 に反映すること
   - APAP 導入時に見直すべき具体的な条件
     （どのエラー種別が APAP 側の責務になるか）を書き残すこと

3. 実 API を叩くテストの扱い
   実プロバイダへの接続は課金が発生し、API キーが必要で、
   外部要因で不安定になります。
   - CI で自動実行するか、opt-in（環境変数やタグで明示的に有効化）にするか
   - キーの管理方法（GitHub Secrets を使うか、ローカル限定にするか）
   - 実行しない場合にテストがスキップされることが、
     「silent green」にならない仕組み
     （スキップされた事実が明示的に見えること。件数0で成功しないこと）

4. 本番プロファイルの起動条件
   P8 で「production プロファイルで Fake が選択されたら起動失敗」という
   ガードを入れており、本番プロファイルは M1 を通じて一度も起動できていません。
   - 実アダプタを配線して本番プロファイルが起動できるようにする
   - ガード自体は残し、Fake が選択された場合は引き続き失敗すること
   - ガードが有効なままであることをテストで確認すること

■ 実装スコープ
- OpenAiExecutionAdapter を本番 DI に配線する
  （プロファイルまたは設定で Fake と切り替えられること）
- API キーを SecretManagerAdapter 経由で供給する経路の実配線
- ModelProfile の設定（上記1の方針に従う）
- 実プロバイダでの疎通確認と実測
  - レイテンシ（p50 / p99）
  - usage の実際の値と、コスト算出結果の妥当性
  - Fake との差分（応答形式、所要時間、エラー挙動）
- 本番プロファイルでのコンテナ起動確認
  （M1 の P11 で作った Docker イメージを使い、実際に起動して1リクエスト通すこと）

■ テスト要件
- 本番プロファイルで実アダプタが選択され、起動できること
- 本番プロファイルで Fake が選択された場合は引き続き起動失敗すること
- API キーが SecretManagerAdapter 経由で解決され、
  ログ・例外・メトリクス・設定ダンプに実値が出ないこと（経路別テスト）
- ModelProfile の設定値が Optimization と Cost 算出に正しく反映されること
- 実 API テストは上記3の方針に従う。スキップされた場合に
  それが明示的に分かること
- 新規追加コードの未カバー分岐を3分類で監査
- カバレッジは buildSrc の下限を下回らないこと

■ 報告事項
実プロバイダで初めて動かすフェーズなので、以下を必ず報告してください。
- Fake でしか通っていなかった経路のうち、実物で挙動が違ったもの
- ADR-0014 / ADR-0029 で決めた前提のうち、実物で崩れたもの
- 実測したレイテンシ・usage・コストと、設定値との乖離
